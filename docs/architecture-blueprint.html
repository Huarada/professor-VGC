ProfessorVGC Blueprint

How the VGC-battle-analysis orchestration is actually wired, at four C4 views (Context, Container, Component, Dynamic), and what shape the data takes at every stage between a pasted replay and the final explanation.

Is there a tool that does this automatically?

No — not one that is both automatic and precise. Nothing in this environment reverse-engineers a codebase into a trustworthy C4 model, and that isn't a gap specific to this toolchain: C4's whole premise is a chosen abstraction boundary — deciding which box counts as a "Container" versus a "Component" — and static analysis can enumerate imports and classes, but it can't make that editorial call. Diagram generators (Structurizr, C4-PlantUML, arch-as-code, IDE dependency graphs) all still require a human to draw the boxes; at best they render a hand-written model.

So this was built the only reliable way: reading src/domain/interfaces.py (the ports), src/services/container.py (the composition root), both AnalysisPipeline implementations, the Node IPC boundary, and every adapter's own docstring — then cross-checked against CLAUDE.md and the ADRs, not copied from either. Written in English per this repo's own language policy (CLAUDE.md §0).

This revision adds Fig. 4, a C4 Dynamic view (the fourth, less-common C4 diagram type — a specific runtime scenario rather than a static structure) for the one thing that changed since the first pass: ADR-028 gave the LangChain explanation stage a bounded loop back into the deterministic/probabilistic ports, where before there was none.

01 System context

Who uses ProfessorVGC, and which outside systems it talks to. Both external data sources are optional-degrading: the app never crashes because one is unreachable.

02 Containers

Inside the ProfessorVGC boundary: one Python process hosting the UI and the application core, plus two long-lived Node.js subprocesses reached over a private stdio JSON protocol (src/adapters/node_ipc.py) — never a network call, never a shared database.

03 Components — inside the Application Core

The Dependency Inversion in practice: two orchestrators sit behind one AnalysisPipeline port and share the same deterministic middle, while every side effect (parsing, calc, Chaos, Smogon, memory, the LLM itself) is a Protocol in src/domain/interfaces.py — the services never import a concrete adapter. One edge breaks the otherwise strictly one-directional flow: since ADR-028, the LangChain explanation agent can call back into three of these same ports on demand (dashed violet arrows below) — see Fig. 4 for how that loop actually runs.

04 Dynamic view — the one loop (ADR-028)

A C4 Dynamic diagram: not a structure, a specific runtime scenario. Every other diagram on this page is a DAG — data flows one way, ending at the explanation. 06 What keeps the model honest

Structural guardrails found in the code, not just stated in prose — the ones that make this architecture, specifically, hard to make hallucinate.

  • Every Node call degrades, never crashes. NodeIpcClient and both *_server.js scripts speak one JSON line in, one JSON line out; a failed lookup returns {ok:false,error} and the Python side falls back (official Smogon → Chaos), rather than raising past the boundary.
  • The cross-side guardrail lives in code, not the prompt. selection_logic.sanitize_plan() physically cannot pair two Pokémon from the same roster — it isn't a rule the 1st AI is asked to follow.
  • The LLM receives one JSON object first, always. build_explanation_context() is still the entire precomputed ground truth handed to stage 9 before anything else — tool access (Fig. 4) only reaches for what that object doesn't contain, and is forbidden by its own prompt addendum from re-deriving a number already in it.
  • The one loop degrades exactly like the IPC boundary does. langchain_tools.py wraps every on-demand call in the same {"ok": false, "error": ...} shape as NodeIpcClient — a bad follow-up lookup ends that tool call, never the whole turn — and it is explicitly bounded (recursion_limit), not open-ended.
  • Two orchestrators, one ground truth — one documented asymmetry. AnalysisService and LangChainAnalysisOrchestrator both import the same MatchupEvaluator/TurnReplaySimulator instances, so every number either backend reports is identical. Only the LangChain backend can also fetch a NEW number on demand (ADR-028) — same shape of accepted asymmetry as ADR-011's unused LangChainLLMProvider.
  • A stale "this is approximate" caveat is treated as a bug. forme_caveat() live-checks forme_resolves() against the real calc engine on each run instead of hardcoding a permanent disclaimer — see ADR-009/ADR-010.
